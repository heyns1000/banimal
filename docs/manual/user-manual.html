Banimal™ Connector Manual

Everything needed to install, configure, and verify the Connector — on a WordPress site today, in a Claude Code profile today, and on every other environment it's headed to next. Every step below matches the real, shipped code; nothing here is aspirational unless it's marked planned.

Overview

Banimal™ Connector is one product doing two jobs through a single thin client: it relays WooCommerce order events to the Banimal™ Cloudflare Worker, and it pulls the verified Sam Fox™ CI Guide from that same Worker to keep a site's brand tokens correct automatically. Nothing about payments, delivery, or brand assets is ever stored twice — the Worker is the one place that holds the truth, and every connected surface reads from it.

This manual covers it in the two places it actually runs today, and where it's headed next:

  • WordPress — the real plugin, installable now.
  • Claude Code — the samfox-ci-guide skill, installable now, so any Claude session applies the same brand rules.
  • Everywhere else — Replit, Lovable, Bolt, and similar — not built yet. Documented honestly as a roadmap, not a feature.

See also: the product page for the pitch, or the Seedwave Atlas for how this fits into the wider ecosystem.

WordPress · Part 1

Install & activate

  1. Check requirements.WordPress 5.9 or later, PHP 7.4 or later.
  2. Copy the plugin folder.Place wordpress-plugin/banimal-ecosystem-connector/ into your site's wp-content/plugins/ directory.
  3. Activate it.Plugins → Installed Plugins → Banimal™ Ecosystem Connector → Activate. A new "Banimal™" menu appears in the admin sidebar.
Before you configure a secret The plugin refuses to store or use a signing secret unless your site has a real AUTH_KEY defined in wp-config.php — 32+ characters, not the default put your unique phrase here placeholder. This is enforced, not a suggestion; the Configuration page shows an error banner until it's fixed.
WordPress · Part 2

Configure the connection

Banimal™ → Configuration. Two fields — nothing else is ever stored here:

FieldWhat it is
Worker API Base URLThe Cloudflare Worker's URL, e.g. https://banimal-worker.example.workers.dev.
Signing SecretThe shared HMAC-SHA256 secret. Leaving this blank on save keeps whatever is already stored — it's never re-encrypted from an empty value.

On the Worker side, the matching secret is set once with:

wrangler secret put WP_BRIDGE_SECRET
What this plugin never stores No Paystack key, no BobGo credential, no GitHub token, no Google Drive credential. Those live exclusively behind the Worker — this plugin holds only the base URL and the one shared secret above.
WordPress · Part 3

Verify it's working

Banimal™ → Diagnostics has two live checks, each hitting the real Worker — never a cached or simulated result:

  • Check Worker Health — calls the Worker's /api/health and shows the raw response.
  • Check Brand Guide — calls /api/brand-guide live (bypassing the plugin's own cache) and shows the current palette and themes.

If you run WooCommerce, change any order's status and confirm a new row appears in the Worker's wp_bridge_events table — that's the signed event pipeline working end to end.

WordPress · Part 4

The brand module

Once configured, every front-end page gets a small, automatic addition to <head> — no theme edits required:

<style id="banimal-brand-tokens">
:root{
  --banimal-ink:#231F20;
  --banimal-cream:#FBF4E4;
  --banimal-sage:#577D60;
  --banimal-coral:#F16B6E;
  /* ...the full verified palette */
}
</style>

Build theme CSS against these variables and the colors stay correct automatically — if the master guide is ever revised, every connected site picks it up within the hour instead of waiting on a manual palette update.

This is cached for one hour per site (WordPress transient) and re-fetched automatically. If the Worker is unreachable, the module is a silent no-op — it will never be the reason a page fails to load.

WordPress · Part 5

Troubleshooting

The Signing Secret field is disabled and won't accept input.
Your AUTH_KEY in wp-config.php is missing, too short, or still the default placeholder. Fix that first — this is a fail-closed guard, not a bug.
Brand tokens aren't appearing in the page source.
Confirm the Worker Base URL is set and reachable via "Check Brand Guide" in Diagnostics. If that check succeeds but tokens still don't appear, clear the banimal_brand_guide_cache transient and reload.
Order status changes aren't reaching the Worker.
The WooCommerce bridge only registers its hooks when WooCommerce is active — confirm it's installed and active, then re-check the signing secret matches on both sides.
Claude Code · Part 1

Install the plugin

The same CI Guide rules the WordPress module applies to a theme are available to any Claude Code session, in three ways — pick whichever fits how you work:

As a plugin (recommended — versioned, works across machines)

claude plugin marketplace add /absolute/path/to/banimal-connector
claude plugin install banimal-connector

As a project skill (this repo only)

mkdir -p .claude/skills
cp -r banimal-connector/skills/samfox-ci-guide .claude/skills/

As a personal skill (every session, every repo, one machine)

mkdir -p ~/.claude/skills
cp -r /path/to/banimal-connector/skills/samfox-ci-guide ~/.claude/skills/
Claude Code · Part 2

Verify it loaded

Ask Claude directly — e.g. "check this against the Sam Fox CI Guide" or "what's the verified palette?" — and it should answer from skills/samfox-ci-guide/SKILL.md rather than guessing from training data: the 9-color palette, the six-move fox-head construction rules, and the wordmark rule that the "o" in "fox" is always the icon, never a typed letter.

Roadmap

Replit, Lovable, Bolt & co. planned

Nothing is built for these yet — this section exists so the pattern is decided once, not reinvented per platform when the time comes. Every future adapter follows the same shape as the two that already exist:

  1. Pull, never push.The adapter fetches GET /api/brand-guide itself; the Worker never needs inbound access to Replit, Lovable, or any other builder.
  2. No local copy of the truth.Palette and icon come from the Worker every time (with a short cache, matching the WordPress module's one-hour transient) — never hand-copied into the app's own source.
  3. Same two icon files./api/brand-guide/icon/ink.png and .../cream.png are the only fox-head assets any adapter should ever reference.

Building one of these adapters means implementing exactly this fetch-and-apply loop for that platform's own theming or component system — not designing a new protocol.

API reference

All three endpoints below are served by the same Banimal™ Worker your Worker API Base URL points to.

GET /api/brand-guide

Public, unauthenticated. Returns the palette, the 9 themes, icon URLs, typography, and compliance text as JSON. Cache-Control: 1 hour.

GET /api/brand-guide/icon/ink.png
GET /api/brand-guide/icon/cream.png

Public, unauthenticated. The verified fox-head mark as PNG bytes. Cache-Control: 24 hours.

POST /api/wp/events

Requires an X-Banimal-Signature header (HMAC-SHA256 over the raw body). Used by the WordPress WooCommerce bridge only — not for direct use.

FAQ

Do I need WooCommerce to use this plugin?
No. The brand module works on any WordPress site. The commerce bridge simply does nothing until WooCommerce is active.
Is the brand guide endpoint safe to call from anywhere?
Yes — it's public and unauthenticated by design. Palette and icon rules aren't secrets; only order events require signing.
What happens if Sam Fox revises the CI Guide?
Update docs/brand/ci-guide.html and the matching values in src/worker/routes/brand-guide.ts. Every connected WordPress site picks up the change within an hour; no plugin update required.
Can I use this outside the Banimal™/Fruitful ecosystem?
The commerce bridge is specific to this Worker. The brand-guide pattern — pull tokens and an icon from one endpoint — is general and is exactly what a future non-WordPress adapter would reuse.
